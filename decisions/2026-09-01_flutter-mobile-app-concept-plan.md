# Концепция и план: мобильное приложение OGE-9-Tutor на Flutter/Dart (автономный режим)

> Статус: **предложение, ожидает подтверждения владельца.** Ничего из
> описанного ниже не реализовано и не начато — ни один файл кода не
> создан. Это документ для обсуждения, следующий шаг — явное «приступай»
> по конкретной фазе (см. «Открытые вопросы» в конце).

## 1. Что это и зачем

Мобильная версия пользовательского режима OGE-9-Tutor-GUI-Assistant
(изучение тем, тесты, прогресс) на Flutter/Dart, способная работать
**полностью автономно** — без запущенного FastAPI-бэкенда, без
интернета, без ключей LLM-провайдера. Административный режим (кэш,
логи, пользователи, RAG-менеджер, LLM-монитор) в объём мобильного
приложения не входит — это инструмент отладки для разработчика/
владельца, ученику он не нужен.

## 2. Ключевое архитектурное решение

Текущее десктопное приложение по умолчанию **не** автономно: реальная
генерация тестов и развёрнутых ответов идёт через LLM API (GPT-4o-mini
через proxyAPI), а поиск по настоящей базе ФИПИ
(`RAG_data_base/vector_db/`) эмбеддит **сам запрос** через OpenAI API
(`text-embedding-3-small`, 1536 измерений) — без сети это не работает
вообще, только зашитый keyword-фолбэк (`LLMClient._generate_fallback`,
`TestGenerator._generate_demo_questions`).

Для мобильного приложения в автономном режиме это нужно перевернуть:
**офлайн — основной режим, а не запасной.** Онлайн-обогащение (если
вообще понадобится) — необязательная надстройка сверху, а не то, без
чего приложение не работает.

Прямое следствие: реальную базу ФИПИ с OpenAI-эмбеддингами **нельзя**
использовать на мобильном устройстве как есть — офлайн-эмбеддинг
запроса тем же эмбеддером, что использовал OpenAI, невозможен (это
закрытая модель, доступная только через API). Нужен **собственный,
открытый эмбеддер, который можно исполнить на устройстве.**

Здесь есть готовое решение внутри самого проекта: `api/vector_store.py`
уже реализует локальный fallback на `sentence-transformers`
(`cointegrated/rubert-tiny2`, 768 измерений) — маленькая модель
(~45 МБ), уже выбранная в этом кодовой базе именно как офлайн-путь.
План использует **её же**, экспортированную в ONNX/TFLite для
инференса на устройстве, а не изобретает третье эмбеддинг-пространство
(в `CLAUDE.md` уже есть явное предостережение не путать/не смешивать
OpenAI- и sentence-transformers-эмбеддинги — здесь то же правило,
применённое к мобильной платформе).

## 3. Что переносится, что перерабатывается, что не переносится

| Из десктопа | Судьба на мобильном |
|---|---|
| 6 тем ФИПИ (`topic_study.py::TOPICS`) | Переносится как есть — это canonical список |
| `LLMClient._generate_fallback()` — 6 тем, keyword-ответы | Переносится как **основной** (не запасной) источник обучающего текста, расширяется до полноценных статей |
| `TestGenerator._generate_demo_questions()` — 6×5 вопросов | Переносится как основа банка тестов, расширяется по объёму (см. Фазу 1) |
| Реальная база ФИПИ, 204 чанка, OpenAI-эмбеддинги | **Не переносится в текущем виде.** Тексты чанков — да (после очистки, см. Находку 1 в `ONBOARDING_ROADMAP.md`); эмбеддинги — нет, переэмбеддятся локально через rubert-tiny2 |
| FastAPI-бэкенд, Redis-кэш | Не нужен для автономного режима — вся логика на устройстве |
| Административный режим целиком | Не входит в объём мобильного приложения |
| Tkinter/ttkbootstrap UI | Не переносится буквально — новый UI на Flutter/Material 3 с нуля, тот же функциональный состав экранов |

## 4. Функциональный объём v1 (MVP, полностью автономный)

- **Изучение тем** — список 6 официальных тем ФИПИ → статья по теме.
- **Тесты** — выбор темы → тест из локального банка вопросов, таймер,
  подсчёт результата.
- **Прогресс** — темы изучены, тестов пройдено, точность, история —
  хранится локально на устройстве.
- **Помощь** — статичный экран, аналог `HelpPanel`.

Без семантического поиска по базе ФИПИ (это Фаза 2) и без реального
LLM (это опциональная Фаза 3) — приложение уже полноценно работает
и приносит пользу на этом уровне.

## 5. Технологический стек (рекомендации, отмечены открытые альтернативы)

| Слой | Рекомендация | Альтернатива |
|---|---|---|
| Управление состоянием | **Riverpod** — современный, тестируемый, хорошо ложится на асинхронные локальные данные | Provider (проще, но менее строгий), Bloc (больше boilerplate) |
| Локальное хранилище (прогресс/история) | **Drift** (SQLite, типизированные миграции) — данные будут расти со временем использования | Hive/Isar (документ-хранилище, быстрее стартовать, меньше строгости схемы) |
| Навигация | go_router | Navigator 2.0 напрямую |
| Офлайн-эмбеддинг (Фаза 2) | `onnxruntime` (или `tflite_flutter`) + экспортированный ONNX rubert-tiny2 | on-device LLM (Gemma и т.п.) — избыточно тяжело для простого эмбеддинга |
| Линт/CI | `flutter_lints` + GitHub Actions (`flutter analyze` + `flutter test`, оба блокирующие) | — |

## 6. Структура приложения (набросок)

```
lib/
  core/            # тема (Material 3, тёмная/светлая), роутинг, DI
  data/
    assets/        # чтение бандла topics.json / questions.json / chunks.json
    local_db/      # Drift-схема: progress, history
    embeddings/    # (Фаза 2) ONNX-инференс + косинусный поиск
  features/
    topics/        # список тем, экран статьи
    tests/         # прохождение теста, таймер, результат
    progress/       # прогресс/история
    help/
assets/
  data/
    topics.json      # экспортировано из LLMClient._generate_fallback
    questions.json   # экспортировано из TestGenerator._generate_demo_questions
    chunks.json      # (Фаза 2) очищенные чанки ФИПИ + вектора rubert-tiny2
  models/
    rubert_tiny2.onnx  # (Фаза 2)
```

## 7. Мост данных: экспорт контента из Python в Flutter

Весь обучающий контент по-прежнему авторится **один раз в Python**
(там же, где он уже есть и уже проверен фактчеком в этой сессии) и
**механически экспортируется** в JSON-ассеты мобильного приложения —
не дублируется вручную. Новый скрипт `scripts/export_mobile_assets.py`
в `OGE-9-Tutor-GUI-Assistant`:

1. Читает 6 тем из `LLMClient._generate_fallback()` (расширенные до
   полноценных статей — текущие абзацы задуманы как faq/фолбэк-ответ,
   не как учебная статья, для мобильного MVP нужно больше текста на
   тему).
2. Читает банк вопросов из `TestGenerator._generate_demo_questions()`
   (тоже расширить — 5 вопросов на тему мало для полноценного теста,
   нужно хотя бы 15–20).
3. (Фаза 2) Читает очищенные чанки `RAG_data_base/vector_db/
   dataset.json`, прогоняет через `sentence-transformers`
   (`cointegrated/rubert-tiny2`) офлайн одним запуском, сохраняет
   вектора вместе с текстом в `chunks.json`.
4. Пишет результат прямо в `assets/data/` мобильного репозитория.

## 8. Поэтапный план

Оценки объёма — грубые ориентиры (в днях сфокусированной работы), не
жёсткое обязательство.

### Фаза 0 — Настройка проекта (0.5–1 день)
- `flutter create`, структура папок (см. раздел 6).
- `pubspec.yaml`: riverpod, drift (или hive), go_router, flutter_lints.
- CI: GitHub Actions, `flutter analyze` + `flutter test`, оба
  блокирующие — по прецеденту, уже установленному в обоих репозиториях
  пары (строгий CI — не необязательная надстройка).
- Новый репозиторий на GitHub, регистрация в `projects-registry.md`
  агента `01_vibe-coding-agent`, по аналогии с двумя существующими.

### Фаза 1 — Автономное ядро (MVP), 3–5 дней
- `export_mobile_assets.py`, расширение контента тем и банка вопросов
  в Python-источниках.
- 4 экрана из раздела 4, локальное хранилище прогресса на Drift.
- Полностью рабочее приложение без сети и без сервера.

### Фаза 2 — Офлайн-семантический поиск по базе ФИПИ, 4–7 дней
- **Зависит от Находки 1** (`ONBOARDING_ROADMAP.md` в этом репозитории)
  — качество данных базы ФИПИ сейчас плохое (мусорные чанки,
  разорванный по буквам текст, обрыв слов). Экспортировать в мобильное
  приложение стоит **после** чистки на стороне Squeezer, иначе мусор
  просто переедет на телефон в новом виде.
- Переэмбеддинг очищенных чанков через rubert-tiny2, экспорт ONNX.
- On-device инференс эмбеддинга запроса + косинусный поиск полным
  перебором по 204 векторам (768 измерений × 204 ≈ 630 КБ — тривиально
  для любого устройства, ANN-индекс не нужен на таком объёме).

### Фаза 3 — Опциональный онлайн-слой (за флагом), 3–5 дней
- Если у пользователя есть сеть и он ввёл свой API-ключ — приложение
  может по желанию обратиться к реальному LLM за более развёрнутым
  ответом, по аналогии с текущим десктопным поведением.
- Строго опционально: приложение обязано оставаться полностью
  работоспособным без этого слоя — это не костыль поверх «настоящего»
  режима, а необязательная надстройка поверх настоящего автономного
  режима.

### Фаза 4 — Полировка и публикация, 3–5 дней
- Material 3, тёмная/светлая тема, адаптивная вёрстка.
- Иконка, сплэш-экран.
- Тестирование на реальных устройствах/эмуляторах.
- Публикация — см. открытый вопрос 7 ниже.

**Итого ориентировочно**: Фазы 0–2 (полноценный автономный MVP
с семантическим поиском) — около 2–3.5 недель; Фазы 3–4 — ещё
1–1.5 недели сверху.

## 9. Открытые вопросы (решает владелец)

1. **Репозиторий** — новый отдельный репозиторий (например,
   `OGE-9-Tutor-Mobile`), по аналогии с текущей парой Squeezer/
   OGE-Tutor, или подпапка внутри существующего
   `OGE-9-Tutor-GUI-Assistant`?
2. **Платформы** — только Android для MVP, или сразу Android + iOS
   (технически из одного Flutter-кода бесплатно, но подпись/публикация
   в App Store — отдельные усилия и аккаунт разработчика Apple)?
3. **Порядок фаз** — начинать ли с Фазы 1 (автономное ядро без
   семантического поиска) уже сейчас, отложив Фазу 2 до закрытия
   Находки 1 в Squeezer, как предложено выше — или ждать чистки данных
   прежде, чем начинать вообще что-либо?
4. **Нужна ли Фаза 3 вообще** — или сознательно оставить приложение
   навсегда чисто автономным (проще, меньше поверхности для секретов/
   багов на устройстве, ключ API на телефоне пользователя — отдельный
   вопрос безопасности)?
5. **Хранилище** — Drift или Hive/Isar (см. раздел 5)?
6. **Публикация** — есть ли уже аккаунт разработчика Google Play, или
   для MVP распространять только как APK напрямую?

## Что не в объёме (осознанно)

- Административный режим (кэш/логи/пользователи/RAG-менеджер/
  LLM-монитор) — инструмент разработчика, не ученика.
- Адаптивная генерация тестов через on-device LLM (Gemma и т.п.) —
  избыточно тяжело (модели от ~1.5 ГБ) для первого релиза; банк
  вопросов фиксированный, расширяемый вручную/скриптом.
- Синхронизация прогресса между устройствами/облаком — не запрошено,
  не входит в определение «автономный режим».
