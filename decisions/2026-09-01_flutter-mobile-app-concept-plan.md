# Концепция и план: мобильное приложение OGE-9-Tutor на Flutter/Dart (автономный режим)

> Статус: **все 5 фаз (0–4) реализованы 2026-09-01.** MVP работает на
> реальном устройстве (Redmi Note 8T) — автономный режим, серверный
> режим, офлайн-семантический поиск, иконка/сплэш, релизный APK передан
> владельцу. Не входит в объём: публикация в Google Play (нет
> аккаунта), сборка/тестирование iOS (нет macOS/аккаунта Apple).

## 1. Что это и зачем

Мобильная версия пользовательского режима OGE-9-Tutor-GUI-Assistant
(изучение тем, тесты, прогресс) на Flutter/Dart, способная работать
**полностью автономно** — без запущенного FastAPI-бэкенда, без
интернета, без ключей LLM-провайдера. Административный режим (кэш,
логи, пользователи, RAG-менеджер, LLM-монитор) в объём мобильного
приложения не входит — это инструмент отладки для разработчика/
владельца, ученику он не нужен.

## 2. Ключевое архитектурное решение

> **Уточнение владельца (ответ на открытый вопрос 4, см. раздел 9):**
> мобильное приложение — это не отдельный офлайн-продукт, а
> **альтернативный фронтенд той же программы**: пользователь должен
> уметь работать с одним и тем же сервером и с компьютера, и с
> телефона — какой удобнее в моменте. Это меняет статус Фазы 3
> (раздел 8): она была описана как необязательная надстройка «для
> кого-то с ключом API»; теперь это **второй полноценный режим** —
> подключение к тому же FastAPI-бэкенду, что уже обслуживает десктоп,
> а не отдельный опциональный вызов LLM. Автономный режим остаётся
> обязательным (исходное требование владельца), но не единственным —
> оба режима равноценны, переключение между ними — выбор пользователя,
> а не запасной путь на случай отсутствия сети.

Текущее десктопное приложение по умолчанию **не** автономно: реальная
генерация тестов и развёрнутых ответов идёт через LLM API (GPT-4o-mini
через proxyAPI), а поиск по настоящей базе ФИПИ
(`RAG_data_base/vector_db/`) эмбеддит **сам запрос** через OpenAI API
(`text-embedding-3-small`, 1536 измерений) — без сети это не работает
вообще, только зашитый keyword-фолбэк (`LLMClient._generate_fallback`,
`TestGenerator._generate_demo_questions`).

Для мобильного приложения в автономном режиме это нужно перевернуть:
**офлайн — основной режим, а не запасной.** Онлайн-обогащение (если
вообще понадобится) — необязательная надстройка сверху, а не то, без
чего приложение не работает.

Прямое следствие: реальную базу ФИПИ с OpenAI-эмбеддингами **нельзя**
использовать на мобильном устройстве как есть — офлайн-эмбеддинг
запроса тем же эмбеддером, что использовал OpenAI, невозможен (это
закрытая модель, доступная только через API). Нужен **собственный,
открытый эмбеддер, который можно исполнить на устройстве.**

Здесь есть готовое решение внутри самого проекта: `api/vector_store.py`
уже реализует локальный fallback на `sentence-transformers`
(`cointegrated/rubert-tiny2`, 312 измерений — уточнено при реализации
Фазы 2, черновая цифра 768 в более ранней версии этого плана была
неверна) — маленькая модель
(~45 МБ), уже выбранная в этом кодовой базе именно как офлайн-путь.
План использует **её же**, экспортированную в ONNX/TFLite для
инференса на устройстве, а не изобретает третье эмбеддинг-пространство
(в `CLAUDE.md` уже есть явное предостережение не путать/не смешивать
OpenAI- и sentence-transformers-эмбеддинги — здесь то же правило,
применённое к мобильной платформе).

## 3. Что переносится, что перерабатывается, что не переносится

| Из десктопа | Судьба на мобильном |
|---|---|
| 6 тем ФИПИ (`topic_study.py::TOPICS`) | Переносится как есть — это canonical список |
| `LLMClient._generate_fallback()` — 6 тем, keyword-ответы | Переносится как **основной** (не запасной) источник обучающего текста, расширяется до полноценных статей |
| `TestGenerator._generate_demo_questions()` — 6×5 вопросов | Переносится как основа банка тестов, расширяется по объёму (см. Фазу 1) |
| Реальная база ФИПИ, 204 чанка, OpenAI-эмбеддинги | **Не переносится в текущем виде.** Тексты чанков — да (после очистки, см. Находку 1 в `ONBOARDING_ROADMAP.md`); эмбеддинги — нет, переэмбеддятся локально через rubert-tiny2 |
| FastAPI-бэкенд, Redis-кэш | Не нужен для автономного режима — вся логика на устройстве |
| Административный режим целиком | Не входит в объём мобильного приложения |
| Tkinter/ttkbootstrap UI | Не переносится буквально — новый UI на Flutter/Material 3 с нуля, тот же функциональный состав экранов |

## 4. Функциональный объём v1 (MVP, полностью автономный)

- **Изучение тем** — список 6 официальных тем ФИПИ → статья по теме.
- **Тесты** — выбор темы → тест из локального банка вопросов, таймер,
  подсчёт результата.
- **Прогресс** — темы изучены, тестов пройдено, точность, история —
  хранится локально на устройстве.
- **Помощь** — статичный экран, аналог `HelpPanel`.

Без семантического поиска по базе ФИПИ (это Фаза 2) и без реального
LLM (это опциональная Фаза 3) — приложение уже полноценно работает
и приносит пользу на этом уровне.

## 5. Технологический стек (рекомендации, отмечены открытые альтернативы)

| Слой | Рекомендация | Альтернатива |
|---|---|---|
| Управление состоянием | **Riverpod** — современный, тестируемый, хорошо ложится на асинхронные локальные данные | Provider (проще, но менее строгий), Bloc (больше boilerplate) |
| Локальное хранилище (прогресс/история) | **Drift** (SQLite, типизированные миграции) — решено (открытый вопрос 5): данные растут со временем использования, а серверный режим (Фаза 3) добавит синхронизацию статусов позже — типизированная схема с миграциями окупится раньше, чем в чисто автономном приложении | ~~Hive/Isar~~ — отклонено, схема менее строгая |
| Навигация | go_router | Navigator 2.0 напрямую |
| Офлайн-эмбеддинг (Фаза 2) | `onnxruntime` (или `tflite_flutter`) + экспортированный ONNX rubert-tiny2 | on-device LLM (Gemma и т.п.) — избыточно тяжело для простого эмбеддинга |
| Серверный клиент (Фаза 3) | `dio` или `http` + типизированные модели, повторяющие схему ответов FastAPI-эндпоинтов десктопа | GraphQL-обёртка — не нужна, бэкенд уже REST |
| Линт/CI | `flutter_lints` + GitHub Actions (`flutter analyze` + `flutter test`, оба блокирующие, тот же workflow-файл, что у Python-части репозитория — не отдельная регистрация проекта) | — |

## 6. Структура приложения (набросок)

Решено (открытый вопрос 1): не отдельный репозиторий — новая папка
`mobile/` внутри этого репозитория (`OGE-9-Tutor-GUI-Assistant/mobile/`).
Один общий `.github/workflows/` каталог, один `decisions/`, одна
`ONBOARDING_ROADMAP.md` — Flutter-часть просто ещё один раздел в них,
без дублирования инфраструктуры, которая уже есть для Python-части.

```
mobile/
  lib/
    core/            # тема (Material 3, тёмная/светлая), роутинг, DI
    data/
      assets/        # чтение бандла topics.json / questions.json / chunks.json
      local_db/      # Drift-схема: progress, history
      embeddings/    # (Фаза 2) ONNX-инференс + косинусный поиск
      remote/        # (Фаза 3) клиент к тому же FastAPI-бэкенду, что у десктопа
    features/
      topics/        # список тем, экран статьи
      tests/         # прохождение теста, таймер, результат
      progress/       # прогресс/история
      settings/      # (Фаза 3) адрес сервера, переключение локальный/серверный режим
      help/
  assets/
    data/
      topics.json      # экспортировано из LLMClient._generate_fallback
      questions.json   # экспортировано из TestGenerator._generate_demo_questions
      chunks.json      # (Фаза 2) очищенные чанки ФИПИ + вектора rubert-tiny2
    models/
      rubert_tiny2.onnx  # (Фаза 2)
```

Платформы (открытый вопрос 2): проект создаётся с таргетами Android +
iOS с самого начала (`flutter create` генерирует оба каталога бесплатно
— задел на будущее ничего не стоит сейчас), но **сборка, тестирование
на устройстве и публикация — только Android** до появления аккаунта
разработчика Apple. CI-джоб для iOS не заводится, пока в этом нет
практической пользы (нечего тестировать и негде публиковать).

## 7. Мост данных: экспорт контента из Python в Flutter

Весь обучающий контент по-прежнему авторится **один раз в Python**
(там же, где он уже есть и уже проверен фактчеком в этой сессии) и
**механически экспортируется** в JSON-ассеты мобильного приложения —
не дублируется вручную. Новый скрипт `scripts/export_mobile_assets.py`
в `OGE-9-Tutor-GUI-Assistant`:

1. Читает 6 тем из `LLMClient._generate_fallback()` (расширенные до
   полноценных статей — текущие абзацы задуманы как faq/фолбэк-ответ,
   не как учебная статья, для мобильного MVP нужно больше текста на
   тему).
2. Читает банк вопросов из `TestGenerator._generate_demo_questions()`
   (тоже расширить — 5 вопросов на тему мало для полноценного теста,
   нужно хотя бы 15–20).
3. (Фаза 2) Читает очищенные чанки `RAG_data_base/vector_db/
   dataset.json`, прогоняет через `sentence-transformers`
   (`cointegrated/rubert-tiny2`) офлайн одним запуском, сохраняет
   вектора вместе с текстом в `chunks.json`.
4. Пишет результат прямо в `mobile/assets/data/`.

## 8. Поэтапный план

Оценки объёма — грубые ориентиры (в днях сфокусированной работы), не
жёсткое обязательство. Порядок фаз (открытый вопрос 3 — «сама установи
порядок») пересобран под ответы владельца: не ждать чистки данных
ФИПИ, чтобы начать хоть что-то, и учесть, что Фаза 3 (раздел 2)
перестала быть опциональной надстройкой — теперь это второй
равноценный режим работы.

**Выбранный порядок и почему:** Фаза 0 → Фаза 1 → **Фаза 3** → Фаза 2
→ Фаза 4. Фаза 3 (серверный клиент) переставлена перед Фазой 2
(офлайн-поиск), потому что она не зависит от чистки данных ФИПИ вообще
— бэкенд и его эндпоинты уже существуют и работают, это интеграция с
готовым, а не разработка нового ML-пайплайна. Так пользователь получает
второй режим работы («программа с телефона») раньше, а Фаза 2 стартует
тогда, когда чистка данных ФИПИ в Squeezer действительно готова —
без гадания сроков наперёд («потом будем править» — если к моменту
старта Фазы 2 чистка ещё не закончена, экспортируем то, что есть, и
дочищаем по факту, не блокируя всё остальное этим ожиданием).

### Фаза 0 — Настройка проекта (0.5–1 день)
- `flutter create` внутри `mobile/` (не отдельный репозиторий — решено,
  открытый вопрос 1), структура папок (см. раздел 6), таргеты
  Android + iOS сразу, сборка/публикация пока только Android (открытый
  вопрос 2).
- `pubspec.yaml`: riverpod, drift, go_router, flutter_lints.
- CI: тот же `.github/workflows/`, что у Python-части репозитория,
  новый job `flutter analyze` + `flutter test`, оба блокирующие — по
  прецеденту, уже установленному в обоих репозиториях пары.

### Фаза 1 — Автономное ядро (MVP), 3–5 дней
- `export_mobile_assets.py`, расширение контента тем и банка вопросов
  в Python-источниках.
- 4 экрана из раздела 4, локальное хранилище прогресса на Drift.
- Полностью рабочее приложение без сети и без сервера — обязательный
  режим (исходное требование владельца), не запасной вариант.

### Фаза 3 — Серверный режим: тот же бэкенд, что у десктопа, 5–8 дней
- Экран настроек: адрес сервера, переключение локальный/серверный
  режим (или автоопределение — пробуем сервер, при недоступности
  падаем в локальный режим прозрачно для пользователя).
- Клиент к тем же FastAPI-эндпоинтам, что уже использует десктопное
  приложение (изучение тем, генерация тестов через LLM, RAG-поиск по
  настоящей базе ФИПИ с OpenAI-эмбеддингами — сервер уже умеет это
  делать, телефону не нужно повторять эту логику локально).
- Оценка объёма выросла относительно первой версии плана (была
  «3–5 дней, опциональный флаг с ключом API») — теперь это полноценный
  API-клиент, а не разовый вызов LLM.

### Фаза 2 — Офлайн-семантический поиск по базе ФИПИ, 4–7 дней
- Идёт параллельно чистке данных на стороне Squeezer (Находка 1,
  `ONBOARDING_ROADMAP.md` в этом репозитории), не после неё — старт
  Фазы 2 не блокируется ожиданием чистки; если к этому моменту чистка
  ещё не закончена, экспортируем текущее состояние данных и дочищаем
  по факту.
- Переэмбеддинг чанков через rubert-tiny2 (пулинг по CLS-токену, не
  усреднение — см. уточнение выше), экспорт ONNX.
- On-device инференс эмбеддинга запроса + косинусный поиск полным
  перебором по 157 векторам (312 измерений × 157 ≈ 196 КБ бинарно,
  ~1.5 МБ в JSON — тривиально для любого устройства, ANN-индекс не
  нужен на таком объёме). Число чанков менялось несколько раз за время
  реализации Фазы 2: 204 на момент написания плана → 197 после первой
  чистки явного мусора → 157 после полного перечанкования и
  переэмбеддинга исходного PDF на исправленном пайплайне Squeezer
  (`pdfplumber` вместо `pypdf`, починенное определение заголовков) —
  экспорт мобильных ассетов синхронизирован с финальной версией.

### Фаза 4 — Полировка и публикация, 3–5 дней — ВЫПОЛНЕНО 2026-09-01
- [x] Material 3, тёмная/светлая тема, адаптивная вёрстка — было готово
  с Фазы 0 (`core/theme.dart`), подтверждено на реальном устройстве.
- [x] Иконка — нарисована с нуля (`scripts/generate_app_icon.py`,
  Pillow), не сторонним генератором из фото/логотипа — академическая
  шапочка на индиго-фоне, подтверждена владельцем.
- [x] Сплэш-экран — сгенерирован `flutter_native_splash`, подтверждён
  на устройстве.
- [x] Тестирование на реальном устройстве (Android) — Redmi Note 8T,
  включая релизную (не debug) сборку после R8-минификации.
- [x] Публикация: APK передан владельцу напрямую (собран с
  `--split-per-abi` — 57.7 МБ для `arm64-v8a` вместо 129.8 МБ на все
  архитектуры сразу). Google Play осознанно вне объёма (решено,
  открытый вопрос 6) — аккаунта разработчика нет.
- Подробности и найденные по пути ограничения сторонних пакетов
  (`flutter_launcher_icons`, `flutter_native_splash` не собирались
  напрямую под Kotlin DSL Gradle этого проекта) — `decision-log.md`.

**Итого ориентировочно**: Фазы 0–1 (автономный MVP) — около 1–1.5
недели; плюс Фаза 3 (серверный режим) — 1–1.5 недели; плюс Фаза 2
(офлайн-поиск, параллельно чистке данных) — ещё около недели; Фаза 4 —
неделя сверху.

## 9. Открытые вопросы — решены (ответы владельца, 2026-09-01)

1. **Репозиторий** — подпапка `mobile/` внутри существующего
   `OGE-9-Tutor-GUI-Assistant`, не отдельный репозиторий.
2. **Платформы** — тестирование, сборка и публикация сейчас только
   Android (аккаунт разработчика Apple, тестовые устройства и подписка
   недоступны); проект заводится сразу с таргетами Android + iOS
   («задел на будущий этап с Apple»), но iOS-специфичная работа
   (подпись, TestFlight, CI-джоб) не начинается, пока в этом нет
   практической пользы.
3. **Порядок фаз** — решение отдано мне: начинать работу сейчас, не
   дожидаясь чистки данных ФИПИ («делать надо, потом будем править,
   чистка будет идти параллельно»). Выбранный порядок и обоснование —
   раздел 8: Фаза 0 → Фаза 1 → Фаза 3 → Фаза 2 → Фаза 4.
4. **Нужна ли Фаза 3** — да, и не как опциональная надстройка: мобильное
   приложение задумано как **альтернативный фронтенд той же программы**
   («пользователь может общаться с сервером через компьютер или телефон
   — как ему удобнее»). Это подняло статус Фазы 3 до полноценного
   второго режима работы — см. уточнение в разделе 2 и пересмотренную
   Фазу 3 в разделе 8.
5. **Хранилище** — Drift (решение оставлено мне: «выбери, что
   правильнее»); обоснование — раздел 5.
6. **Публикация** — пока только APK напрямую, аккаунта Google Play нет.

## Что не в объёме (осознанно)

- Административный режим (кэш/логи/пользователи/RAG-менеджер/
  LLM-монитор) — инструмент разработчика, не ученика.
- Адаптивная генерация тестов через on-device LLM (Gemma и т.п.) —
  избыточно тяжело (модели от ~1.5 ГБ) для первого релиза; банк
  вопросов фиксированный, расширяемый вручную/скриптом.
- Синхронизация прогресса между устройствами/облаком — не запрошено,
  не входит в определение «автономный режим».

## 11. Открытый вопрос следующей итерации — качество офлайн-поиска

Приглушение по длине (`local_search.dart`, 2026-09-02,
decision-log) решило самый явный случай — короткие чанки-артефакты
вёрстки («а б в г д») больше не забивают топ-5. **Не решено**:
процедурные фрагменты длиннее 80 символов (списки номеров заданий
вида «задания 1, 15, 19, 20 и 21–24...», копирайт-плашки
«© ФГБНУ ФИПИ...») всё ещё попадают в топ выдачи — демпфирование по
длине их не касается, они не короче порога, но и не содержательны
по существу вопроса. Кандидаты на исправление (не выбран ни один,
решение за владельцем):

- Поднять порог демпфирования выше 80 символов — риск: часть
  легитимного контента средней длины (медиана по датасету — 260
  символов, но есть содержательные абзацы и короче) окажется
  приглушена без разбора.
- Эвристика по паттернам («©», «задания N, N...», нумерованные
  инструкции) — точнее, но требует проверки на всём датасете из
  157 чанков, чтобы не зацепить ложные срабатывания.
- Оставить как есть — уже лучше, чем было, и часть общего вопроса
  качества контента реальной базы ФИПИ (Находка 1, Squeezer) шире,
  чем можно решить только на стороне ранжирования в приложении.
