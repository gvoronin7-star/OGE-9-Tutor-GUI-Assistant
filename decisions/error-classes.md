## 1. Проверка шла не в той среде, где работает результат

Локально, в debug-сборке или на старой сборке всё хорошо, на сервере, в
релизе или у пользователя — нет.

- К-2: `INTERNET` объявлен только в debug/profile-манифестах; серверный
  режим проверяли на debug-APK.
- 10.10: APK от 08.09 16:52 оказался старше исправления `INTERNET`
  того же дня (`7b5ee22`).
- 14.10: `test_initialize` зелёный локально только потому, что в
  `data/chunks/` лежат файлы из `.gitignore`; в CI папка пустая.
- В-15, 14.10: версии инструментов расходятся — black в CI был 26.5.1
  при 24.1.1 в `requirements.txt`; локальный mypy 2.3.1 при 1.8.0 в CI;
  Pillow не объявлен в `requirements.txt`, CI ставит 12.3.0 транзитивно.
- 14.10, приёмка В-14: mypy сверен пиннутой версией, isort — локальной
  9.0.1; CI с isort 5.13.2 упал на формате импорта в новом тесте.

**Как ловить.** Критерий готовности — прогон там, где работает
результат: зелёный CI на сервере, `aapt dump permissions` релизного APK,
сравнение `git log -1 -- mobile/` со временем сборки. Локальная проверка
— теми же версиями инструментов, что закреплены в CI.

## 2. Тест проверяет не то, что заявлено

- В-8: мок атрибута стирался в `initialize()`, тест ходил в HuggingFace;
  единственный assert — `cache_manager is not None`.
- В-8: тавтологии — `assert category in ["top","medium","rare"]` при
  трёх возможных значениях.
- 14.10: `test_initialize` писал демо-чанки в рабочую `data/chunks/`
  репозитория, хотя фикстура `temp_dir` у него была.
- 14.10 (В-14, круг 1 исполнителя): колонка «Время» вкладки «Logs»
  показывала `7.486426` — срез `timestamp[-8:]` при метке с
  микросекундами. Тест проверял только длину строки (8 символов — у
  ошибочного значения тоже 8) и подставлял метку без микросекунд,
  которой настоящий логгер не пишет. Прогоны были зелёными, нашёл снимок
  экрана.

**Как ловить (дополнение).** Входные данные теста — того же вида, что
пишет настоящий код (лучше — записанные им самим); проверять значение,
а не длину или тип.

**Как ловить.** Для каждого теста ответить: какой ввод сделал бы его
красным. Тест не читает и не пишет каталоги репозитория — только
временные. Моки ставить там, где код их резолвит (класс в модуле, не
атрибут экземпляра, который код перезапишет).

## 3. Заявленный статус расходится с фактом

- К-3: три админ-вкладки с выдуманными данными, в README — ✅.
- В-12, В-17: «исправлено полностью», «все 11 закрыты» — данные и сам
  документ этого не подтверждают.
- К-6: README описывает один клиент из двух.
- Аудит 31.08 «path traversal не найдено» — роутер появился позже
  (К-1).
- В-17, поправлено 19.10: `ONBOARDING_ROADMAP.md` — «pytest 36/36» и «CI
  зелёный» при красном CI с 08.09 по 14.10; «все 11 находок закрыты»
  при трёх частичных. Журнал уже знал факт, живой документ — нет.

**Как ловить.** Статус «готово/закрыто/✅» ставится со ссылкой на
проверку (хэш, прогон, команда), которую можно повторить. При
изменении кода — пересмотреть ранее выданные заключения по этой зоне.

## 4. Отказ выглядит как успех

- К-4: любой сбой LLM → шаблонная заглушка, кэшируется на сутки,
  `status="success"`.
- В-9: локальный эмбеддинг всегда даёт `[]` через `except`.
- К-7: «✅ База успешно заменена», когда замена ни на что не влияет.
- К-3: «Соединение установлено успешно» без сетевого вызова.
- В-11: пустой ответ LLM молча подменяется демо-вопросами.

**Как ловить.** У каждого `except` и fallback — признак деградации в
результате (флаг, лог уровня warning, текст в UI). Тест на путь отказа,
а не только на успех.

## 5. Непроверенный ввод на публичной границе

- К-1: `difficulty` из публичного API попадает в имя файла (path
  traversal).
- В-1: API без аутентификации, `num_questions` без верхней границы,
  `str(exc)` наружу.

**Как ловить.** Каждое поле запроса, которое идёт в путь, запрос к
платному API или цикл, — через whitelist/`Literal`/границы в схеме.

## 6. Разрушающая операция до проверки

- К-7: `rmtree` текущей базы до копирования и проверки новой.
- В-14: «Очистить логи» удаляет все `*.csv|*.log` под
  `except Exception`.
- В-6: запуски мутируют файлы под git (`logs/*.csv`, `data/tests/*.json`).

**Как ловить.** Новое — во временное место, проверка, затем атомарная
замена. Ничего, что пишет программа при работе, не лежит под git.

## 7. Неполный поиск даёт ложный вывод о коде

- Урок 12.10 (отправлен хабу): `metrics_panel.py` и соседние модули
  сочтены мёртвыми по grep `from gui_debugger.components.metrics_panel
  import`; на деле они подключены через реэкспорт
  `from gui_debugger.components import MetricsPanel` в `__init__.py`.
- 12.10: карточки статистики в `cache_manager.py` и `llm_monitor.py`
  создавались, но не размещались (`.grid()` не вызывался) — по коду
  выглядели рабочими, на экране их не было.

**Как ловить.** Вывод «не используется» — только после поиска по обоим
способам импорта (`from пакет.модуль import X` и `from пакет import X`)
и, для UI, после живого запуска со снимком экрана.

## 8. Захардкоженное значение вместо источника правды

- В-16: `foreground="#303030"` (цвет светлой темы) при тёмной теме по
  умолчанию — исправлено 12.10.
- М-7: «157 чанков ФИПИ» константой в пяти местах вместо `len(dataset)`.
- В-14: пути GUI от текущего каталога, а не от `project_root`.
- К-5: неверный URL в `.env.example` и документации.

**Как ловить.** Значение, которое уже есть в теме/данных/конфиге,
берётся оттуда. Поиск литерала по всему дереву перед правкой одного
места.
