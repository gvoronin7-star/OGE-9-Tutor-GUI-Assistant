# Архитектура системы OGE Tutor GUI

## Обзор

Система представляет собой десктопное GUI-приложение для подготовки к ОГЭ по обществознанию с RAG-пайплайном. Архитектура построена на принципах клиент-сервер с использованием FastAPI и Tkinter.

## Компоненты системы

### 1. GUI Приложение (Tkinter + ttkbootstrap)

**Назначение**: Пользовательский интерфейс для обучения

**Основные функции**:
- Изучение тем с подробными объяснениями
- Решение тестов с автоматической проверкой
- Отслеживание прогресса обучения
- Административный режим для отладки

**Файлы**:
- `gui_debugger/main.py` — точка входа
- `gui_debugger/app.py` — главное окно
- `gui_debugger/modes/user_mode.py` — пользовательский режим
- `gui_debugger/modes/admin_mode.py` — административный режим

**Компоненты GUI**:
- `main_menu.py` — главное меню
- `topic_study.py` — изучение тем
- `test_solver.py` — решение тестов
- `progress.py` — прогресс обучения
- `log_viewer.py` — просмотр логов

### 2. FastAPI Backend

**Назначение**: REST API для RAG-пайплайна и мониторинга

**Эндпоинты**:
- `GET /` — проверка работоспособности
- `GET /health` — проверка здоровья компонентов
- `GET /metrics` — метрики системы
- `GET /api/topics`, `POST /api/ask`, `POST /api/tests/generate` — для
  мобильного клиента (`../mobile/`) в серверном режиме, `api/mobile_routes.py`

**Файл**: `main.py`

### 3. RAG-Pipeline

**Назначение**: Поиск релевантной информации и генерация ответов

**Компоненты**:

#### 3.1 Векторный поиск (Faiss) — два раздельных хранилища

Не путать: это разные векторные пространства, эмбеддинги одного не
совместимы с индексом другого.

- **`api/vector_store_existing.py` (`ExistingVectorStore`) — реально
  используемое хранилище**, включается флагом `USE_EXISTING_INDEX=true`.
  Читает готовый индекс из `RAG_data_base/vector_db/`
  (157 чанков базы ФИПИ), эмбеддинги OpenAI `text-embedding-3-small`
  (1536-dim), эмбеддит сам запрос через тот же API.
- **`api/vector_store.py` (`VectorStore`) — локальный fallback**,
  пустой по умолчанию, пока `data/chunks/` не наполнены отдельно.
  Индекс: HNSW, модель эмбеддингов `rubert-tiny2` (312-dim на практике,
  не 768 — см. `decisions/decision-log.md`, зональный аудит хаба
  2026-09-08, В-9 отчёта).

#### 3.2 Полнотекстовый поиск (Whoosh)
- **Файл**: `api/text_search.py`
- **Поля**: topic, content, keywords

#### 3.3 LLM-клиент
- **Файл**: `api/llm_client.py`
- **Основная модель**: GPT-4o-mini (через ProxyAPI, единый адрес
  `https://api.proxyapi.ru/v1`)

**Пайплайн**:
1. Получение запроса от GUI
2. Поиск в Faiss (top-5)
3. Поиск в Whoosh (top-3)
4. Объединение и дедупликация результатов
5. Формирование промпта
6. Генерация ответа через LLM
7. Кэширование результата
8. Возврат ответа в GUI

### 4. Система кэширования (Redis)

**Назначение**: Динамическое кэширование ответов

**TTL по категориям**:
- Топ-20% запросов: 24 часа
- Средние запросы: 6 часов
- Редкие запросы: 1 час

**Файл**: `utils/cache.py`

### 5. Логирование

**Файлы**:
- `utils/logger.py` — настройка логирования

**Типы логов**:
- `logs/app.log` — основные логи
- `logs/app.json` — JSON-логи
- `logs/requests.csv` — логи запросов

### 6. Генератор тестов

**Файл**: `api/test_generator.py`

**Функции**:
- Генерация вопросов по теме
- Поддержка разных уровней сложности
- Проверка ответов

## Потоки данных

### Поток 1: Запрос через GUI
```
Пользователь → GUI (Tkinter) → RAG Pipeline → LLM → Ответ → GUI → Пользователь
```

### Поток 2: Поиск информации
```
Запрос → Faiss (векторный) → Whoosh (текстовый) → Объединение → Контекст
```

### Поток 3: Кэширование
```
Запрос → Проверка кэша → (hit: возврат) / (miss: LLM → Сохранение в кэш)
```

### Поток 4: Генерация тестов
```
Выбор темы → Генератор тестов → LLM → Тест с вопросами → GUI
```

## Безопасность

Бэкенд слушает `0.0.0.0:8000` **без аутентификации, CORS-политики и
лимита частоты запросов** — рассчитан на локальную сеть (LAN), не на
публичный интернет (см. `mobile/README.md`). `/api/ask` — платный
вызов LLM на каждый запрос, доступный без ключа кому угодно в той же
сети. Известная находка (В-1, зональный аудит хаба 2026-09-08), решение
о минимальной аутентификации — за владельцем. Валидация входных схем
через Pydantic есть (например, `difficulty`/`num_questions` в
`api/mobile_routes.py` — закрыто К-1 того же аудита), но это защита от
некорректных данных, не от чрезмерного количества запросов.

1. **Изоляция**: компоненты разделены по модулям
2. **Логирование**: успешные и ошибочные запросы записываются
   (`utils/advanced_logger.py`), CSV не в git (см. `.gitignore`)
